# `backend/schemas.py` — Pydantic Request / Response Models

## 1. Purpose & Overview

`backend/schemas.py` defines every Pydantic model that flows across the HTTP boundary of the FastAPI app. It is the **single source of truth for the public API contract** — both the OpenAPI schema generated by FastAPI and the runtime validation of incoming bodies / outgoing responses are derived from these classes.

The file is intentionally small (~100 lines) and dependency-free apart from `pydantic` and `typing`. By isolating DTOs from route handlers, the project gets:

- **Auto-generated OpenAPI docs** with rich field descriptions.
- **Type-safe parsing & validation** of request bodies (`POST`/`PUT`) and query parameters.
- **Self-documenting code** — `Field(..., description="…")` doubles as inline API docs.
- **No business logic in the DTO layer** — pure data shapes, no DB / network calls.

---

## 2. Architecture

```
                  ┌────────────────────────────────┐
   HTTP request   │  FastAPI route handler        │   HTTP response
   JSON body ───► │  function(payload: DTO)       │ ──► JSON body
                  │     payload: <DTO>            │
                  └──────────────┬─────────────────┘
                                 │
                                 ▼
                       backend/schemas.py
                                 │
                  ┌──────────────┴──────────────┐
                  │                             │
        Request DTOs (POST bodies)      Response DTOs (return types)
        ──────────────────────────      ────────────────────────────
        ChatRequest                     ChatResponse
        SessionCreate                   SessionResponse
        ScrapeRequest                   ScrapeResponse
                                       MessageItem
                                       HealthResponse
                                       OpportunityItem
                                       OpportunitiesResponse
                                       TranscribeResponse
                                       OpportunityCard
                                       StructuredChatResponse
                                       ChatMessage (used inside ChatRequest)
```

Schemas are imported by `backend/main.py` and re-exported through the route decorators. They have **no knowledge** of FastAPI itself.

## 3. Key Classes / Functions

All classes subclass `pydantic.BaseModel`. Fields without defaults are required; fields with `default=` or `default_factory=` are optional.

### 3.2 `ChatRequest` — `backend/schemas.py:9`

```python
class ChatRequest(BaseModel):
    prompt: str = Field(..., description="User query prompt")
    session_id: Optional[str] = Field(default=None, description="Optional chat session ID for database persistence")
    conversation_history: List[ChatMessage] = Field(default_factory=list, description="Recent conversation history")
    provider: str = Field(default="Ollama", description="LLM provider: 'Ollama' or 'LLamaCPP'")
    think: bool = Field(default=False, description="Enable thinking/reasoning mode if supported")
    rerank: bool = Field(default=True, description="Enable re-ranking of retrieved document chunks")
    debug: bool = Field(default=False, description="Enable debug mode to expose prompt and retrieval details")
    ollama_base_url: Optional[str] = Field(default=None, description="Optional override for Ollama API server base URL")
    llamacpp_server_url: Optional[str] = Field(default=None, description="Optional override for llama.cpp HTTP server URL")
```

Body of `POST /chat` and `POST /chat/stream`.

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `prompt` | `str` | required | The user's current turn. |
| `session_id` | `Optional[str]` | `None` | If `None`, the non-streaming endpoint calls `create_session()` to make one. The streaming endpoint skips auto-creation. |
| `conversation_history` | `List[ChatMessage]` | `[]` | Used by the RAG pipeline for multi-turn context. |
| `provider` | `str` | `"Ollama"` | Selects the LLM HTTP backend (`"Ollama"` or `"LLamaCPP"`). |
| `think` | `bool` | `False` | Toggle chain-of-thought / thinking mode if the model supports it. |
| `rerank` | `bool` | `True` | Apply a re-ranker to retrieved chunks before generation. |
| `debug` | `bool` | `False` | When true, the pipeline exposes prompts and retrieval info in the response metadata. |
| `ollama_base_url` | `Optional[str]` | `None` | Per-request override; falls back to `settings.model.ollama_base_url`. |
| `llamacpp_server_url` | `Optional[str]` | `None` | Per-request override; falls back to `settings.model.llamacpp_server_url`. |

## 4. Flow / Lifecycle

Schemas have no runtime lifecycle beyond instantiation. The lifecycle of the *data* they carry:

```
client                     FastAPI                          Pydantic                handler
   │                          │                                │                       │
   │  POST /chat (JSON body)  │                                │                       │
   │ ───────────────────────► │   parse body                   │                       │
   │                          │ ─────────────────────────────► │   validate            │
   │                          │                                │ ────────────────────► │
   │                          │                                │     ChatRequest(...)  │
   │                          │                                │                       │ handler runs
   │                          │                                │ ◄──────────────────── │ ChatResponse(...)
   │                          │ ◄────────────────────────────  │   serialize           │
   │ ◄──────────────────────── │  JSON body                     │                       │
```

When a payload fails validation, FastAPI automatically returns `422 Unprocessable Entity` with a structured error body pointing at the offending field. Handlers never see invalid data.

## 5. Dependencies

| --- | --- |
| `pydantic.BaseModel` | Base class for every schema. |

## 8. Error handling

Schemas **propagate** errors, they don't catch them. Validation failures surface to the client as:

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "detail": [
    {
      "loc": ["body", "prompt"],
      "msg": "Field required",
      "type": "missing"
    }
  ]
}
```

There is no custom error formatting in this module; FastAPI's default is sufficient.

> **Caveat for clients.** `OpportunityCard.application_url` is declared but no route serializes it. `StructuredChatResponse` is also unused. Don't write code against these yet.

## 9. Notable patterns / design decisions

- **DTOs are pure data classes.** No methods, no business logic, no I/O. Keeps them easy to evolve and serialize.
- **Defaults match server defaults.** `ChatRequest.provider = "Ollama"`, `ScrapeRequest.days_back = 30`, etc., mirror the server's hard-coded defaults. Clients can omit these fields safely.
- **Optional metadata fields everywhere.** `metadata: Optional[dict] = None` is the convention so that a metadata-less message still serializes cleanly.
- **`description=` is used liberally.** This populates the OpenAPI schema with rich per-field docs (`/docs`), which is the primary "user manual" for the API.
- **Legacy alias strategy lives in handlers, not schemas.** The same model is returned from both `/api/v1/sessions` and the legacy `/sessions` paths — schemas are URL-agnostic.
- **Reserved future-use types.** `OpportunityCard` and `StructuredChatResponse` document the planned shift to fully-structured assistant output without committing handler code yet.
- **`created_at` / `updated_at` are `str`, not `datetime`.** Easier serialization across SQLite (which stores ISO strings) without per-field converters, and consistent with the way the DB layer returns them.
- **No `model_config = ConfigDict(...)` overrides.** Schemas use vanilla Pydantic v2 behavior — `from_attributes` is **not** enabled, so DB rows must be unpacked to dicts (`dict(row)`) before constructing models. This is the convention used throughout `backend/database.py`.
